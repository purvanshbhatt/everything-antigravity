# Database Migrations

A migration is a deploy of shared state that cannot be rolled back by
redeploying code. Every step must be compatible with the application version
before it and after it, every backfill must be resumable, and nothing touches a
shared database without a reviewed plan and an explicit yes.

## When to use

- Writing, reviewing or ordering migration files.
- Renaming, splitting or retyping columns or tables on a live system.
- Backfilling data into a new column or table.
- Adding migration checks to CI or a migration step to CD.

## When not to use

- Which lock each PostgreSQL DDL takes and the per-change SQL recipes: see `database-design` (recipes) and `postgres-patterns`.
- MySQL online DDL tools (`gh-ost`, `pt-online-schema-change`): use `mysql-mariadb`.
- ORM model and query design: use `orm-patterns`.
- Moving data between different systems or engines: use `legacy-modernization` and the `migration-specialist` agent.

## Workflow

1. **Classify the change.** Additive (new table, nullable column, new index), transformational (rename, type change, split) or destructive (drop column or table, tighten constraint).

   **Check:** Transformational and destructive changes are split into expand/contract phases (below), never one migration.

2. **Generate, then read the SQL.** Autogenerated migrations guess; review the SQL they emit.

   ```bash
   alembic revision --autogenerate -m "add order note"; alembic upgrade head --sql   # offline SQL
   python manage.py makemigrations; python manage.py sqlmigrate orders 0042
   npx prisma migrate dev --name add_order_note                                     # dev only
   dotnet ef migrations add AddOrderNote; dotnet ef migrations script --idempotent
   ```

   **Check:** You have read every statement and know the lock it takes and how long it runs at production size.

3. **Make it safe to run.** Set lock and statement timeouts at the top (PostgreSQL `SET lock_timeout = '5s'`; MySQL `SET SESSION lock_wait_timeout = 5`). Keep each migration to one concern. Separate non-transactional steps (`CREATE INDEX CONCURRENTLY`) into their own migration with the tool's no-transaction option. Lint: `squawk` for PostgreSQL SQL files, `atlas migrate lint`, or framework linters (for example Rails `strong_migrations`).

   **Check:** Lint passes, and the migration was applied to a production-sized copy while a load script ran.

4. **Plan backfills as jobs, not migrations.** Run them outside the schema migration transaction, in primary-key batches, idempotent and resumable (see pattern below), throttled on replica lag.

   **Check:** Killing the backfill halfway and restarting it produces the same end state.

5. **Write the rollback story.** Prefer roll-forward fixes. Down migrations that drop data are not rollbacks. For destructive steps, confirm a backup or point-in-time recovery window and record the restore procedure.

   **Check:** The plan states, for every step, what happens if the app is rolled back after it.

6. **Get approval and run.** Present the plan (steps, locks, duration, backfill size, rollback) as an implementation-plan artifact. Run against a shared, staging or production database only after explicit user confirmation, from a single runner: a CI/CD job, Cloud Run job or Kubernetes Job, not on every app replica at startup.

   **Check:** The user approved; the tool's history table (`flyway info`, `alembic current`, `prisma migrate status`) shows the expected version afterwards.

## Patterns

### Expand/contract (rename `name` to `full_name`)

| Release | Schema | Application |
| :--- | :--- | :--- |
| 1. Expand | Add `full_name` nullable | Write both columns, read `name` |
| 2. Backfill | Batch-copy `name` into `full_name` | Unchanged |
| 3. Switch | Add `NOT NULL` safely if needed | Read `full_name`, still write both |
| 4. Contract prep | None | Stop writing `name`; deploy and wait one full release |
| 5. Contract | Drop `name` | None |

Each row is a separate deploy. Any release can be rolled back to the one before it without data loss.

### Resumable backfill

```python
def backfill(conn, batch: int = 5000) -> None:
    last_id = load_checkpoint() or 0
    while True:
        with conn.transaction():
            rows = conn.execute(
                "UPDATE customers SET full_name = name "
                "WHERE id IN (SELECT id FROM customers WHERE id > %s AND full_name IS NULL "
                "ORDER BY id LIMIT %s) RETURNING id", (last_id, batch)).fetchall()
        if not rows:
            break
        last_id = max(r[0] for r in rows)
        save_checkpoint(last_id)
        wait_while_replica_lag_high()
```

The `full_name IS NULL` guard makes reruns safe; the checkpoint makes restarts cheap.

### Tool notes

| Tool | Apply | Status and safety |
| :--- | :--- | :--- |
| Flyway | `flyway migrate` | `flyway info`, `flyway validate` (checksum drift) |
| Liquibase | `liquibase update` | Preconditions; changelog checksums |
| Alembic | `alembic upgrade head` | `alembic heads` shows multiple heads after parallel branches; merge them |
| Django | `python manage.py migrate` | `makemigrations --check` fails CI if models changed without a migration |
| Rails | `bin/rails db:migrate` | `strong_migrations` gem blocks unsafe operations |
| Prisma | `npx prisma migrate deploy` (CI/CD) | Never `migrate dev` or `db push` against shared databases |
| EF Core | Apply an idempotent script or a migration bundle | Avoid `Database.Migrate()` at startup with many replicas |
| golang-migrate | `migrate -path ./migrations -database "$DATABASE_URL" up` | Dirty state after failure needs a manual `force`; investigate first |

### CI checks

1. Apply all migrations to an empty database (Testcontainers or a service container).
2. Apply only the new migrations to a snapshot of the current schema.
3. Detect drift: models versus migrations (`makemigrations --check`, `prisma migrate diff`, `alembic check` in recent versions).
4. Lint for dangerous operations and require a reviewer for destructive ones.
5. Run the previous application version's tests against the new schema to prove backward compatibility.

## Anti-patterns

| Don't | Do instead | Why |
| :--- | :--- | :--- |
| Rename or retype in one migration | Expand/contract across releases | Old pods break the moment the column changes |
| Backfill inside the schema migration | Separate batched, resumable job | Long transactions hold locks and bloat the database |
| Run migrations on app startup across replicas | One runner job before rollout | Races and partial application |
| Edit an applied migration | Add a new migration | Checksums break and environments diverge |
| Trust autogenerate output | Read the SQL and the locks | Autogenerate drops and recreates what it cannot diff |
| Call a data-dropping down migration a rollback | Roll forward, with backups for destructive steps | The data is gone either way |
| Point `prisma db push` or `synchronize` at shared databases | Versioned migrations | Schema changes become untracked and lossy |

## Verification checklist

- [ ] Transformational and destructive changes are split into expand/contract releases.
- [ ] Generated SQL was read, linted, and timed on production-sized data.
- [ ] Lock and statement timeouts are set; non-transactional DDL is isolated.
- [ ] Backfills are batched, idempotent, resumable and throttled.
- [ ] CI applies migrations from empty and from current, and checks drift.
- [ ] The user approved the plan before any shared or production run, with a restore point confirmed.
