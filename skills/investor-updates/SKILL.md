# Investor Updates

Regular, consistent, honest updates build the trust that matters when you need
help or money. Show the same metrics every time, lead with the truth, and make
every ask specific enough that an investor can act on it today.

## When to use

- "Draft this month's investor update", "help me with the board deck", "how do I tell investors we missed?".
- Setting up an update cadence after a round closes.
- Preparing a board pre-read, agenda, resolutions or follow-up notes.
- Reviewing an update for tone, completeness and consistency with previous ones.

## When not to use

- Raising a new round: `pitch-deck`.
- Building the forecast behind the numbers: `financial-modeling`.
- Running the meeting itself (agenda discipline, decisions log): `meeting-facilitation`.
- Questions about disclosure duties, resolutions or securities law: a qualified lawyer.

## Workflow

1. **Set cadence and audience.** Monthly email for investors and angels; quarterly meetings for the board; ad hoc for material events (key hire or departure, large customer loss, runway change). Mark updates confidential and keep customer personal data and secrets out; assume updates may be forwarded.

   **Check:** The user has confirmed the distribution list and how it is sent (individual emails, BCC or a mailing tool).

2. **Pull the numbers from source.** Use the same KPI table every time, computed from billing, the warehouse or the finance sheet, with prior period and plan.

   **Check:** Each number reconciles to its source; any change in a definition since the last update is flagged in a footnote.

3. **Draft from the template below.** Lead with a three-line summary. Keep it short enough to read on a phone.

   **Check:** The summary covers the state of the business, the biggest win and the biggest problem.

4. **Deliver bad news plainly.** State what was missed, the cause, the effect on plan and runway, what you are doing and what help you need. Put it in the summary when it is material.

   **Check:** When any KPI is behind plan, the lowlights section explains it; it is never empty in a bad month.

5. **Review against the previous update.** Find the last update (Gmail sent mail or Drive) and compare: changed metrics explained, previous asks followed up, tone consistent. A subagent can run this comparison and list gaps.

   **Check:** Every metric movement and every previous ask is addressed.

6. **Send only with confirmation.** Create a Gmail draft, show the user the final text and the recipient count, and send only after explicit approval.

   **Check:** The user approved the final draft and recipients.

7. **Prepare board meetings.** Build the deck with the structure below, send the pre-read several business days before the meeting, spend meeting time on discussion and decisions, and have minutes taken by the company secretary or counsel.

   **Check:** The pre-read went out ahead of time; decisions needed are listed on the first slide; minutes and action owners are recorded.

8. **Track asks and thank helpers.** Log each ask, who helped and the result. Thank helpers by name in the next update (with their agreement).

   **Check:** The ask log is updated before the next update is drafted.

## Monthly update template

```markdown
Subject: <Company> update: <Month YYYY> (confidential)

**Summary**
- <State of the business in one line>
- <Biggest win>
- <Biggest problem and what we are doing>

**KPIs**
| Metric | This month | Last month | Plan | Note |
| ARR or MRR | <x> | <x> | <x> | |
| Net new ARR | | | | |
| Customers (paying) | | | | |
| Net / gross revenue retention | | | | |
| Gross margin | | | | |
| Net burn | | | | |
| Cash in bank | | | | |
| Runway (months) | | | | |

**Highlights**   <2-4 bullets with evidence>
**Lowlights**    <what missed, why, what we are doing>
**Asks**         <specific: "Intro to <role> at <company type or named company>", "Candidates for <role>">
**Product**      <what shipped and what it changed>
**Team**         <hires, departures, open roles>
**Thanks**       <who helped with last month's asks>
```

Runway, stated consistently each time:

```text
Net burn (monthly) = cash at start of month - cash at end of month (excluding financing inflows)
Runway (months)    = cash in bank / average net burn over the last 3 months
```

## Board deck structure

| Section | Content |
| :--- | :--- |
| 1. Agenda and decisions needed | The approvals and discussion questions, up front |
| 2. CEO summary | State of the business, KPIs against plan, top risks |
| 3. Financials | P&L against budget, cash, runway, scenarios if runway is short |
| 4. Functional deep dive | One area per meeting, rotating |
| 5. Strategic discussion | One or two questions where board input changes a decision |
| 6. People | Hiring plan, key roles, organization changes |
| 7. Approvals (consent items) | Option grants, budget, policies, as prepared by counsel |
| 8. Executive session | Board-only time, if the board holds one |

## Anti-patterns

| Don't | Do instead | Why |
| :--- | :--- | :--- |
| Change which metrics you show when numbers dip | Keep the KPI table constant | Investors notice and assume the worst |
| Share only good news | Always include lowlights with a plan | Surprises later cost far more trust |
| Write vague asks ("intros welcome") | Name the role, company type or person | Specific asks get answered |
| Read status aloud in board meetings | Send a pre-read; use the meeting for decisions | Board time is the scarcest input |
| Update only when fundraising | Keep a fixed cadence | Consistency is the signal |
| Include customer data or other companies' confidential details | Aggregate and anonymize | Updates get forwarded |
| Send without review | Draft, review, send on explicit approval | Sent updates cannot be recalled |

## Verification checklist

- [ ] The KPI table matches previous updates, with any definition changes footnoted.
- [ ] Every number reconciles to source data.
- [ ] Lowlights are present when results are behind plan.
- [ ] Asks are specific; previous asks are followed up.
- [ ] Runway is computed the same way as last time.
- [ ] The user approved the final text and recipient list before sending.
