# SQL Optimization

Measure first, change one thing, measure again. Most slow SQL comes from a
missing or wrong index, a predicate the index cannot use, a row-count
misestimate, or doing per-row work that should be set-based.

## When to use

- A query, endpoint or report is slow, or database CPU or I/O is saturated.
- A plan regressed after a deploy, data growth or a version upgrade.
- Pagination degrades on later pages.
- A backfill, import or bulk update must run without hurting production.

## When not to use

- Schema and type design from scratch: use `database-design`.
- Engine-specific features (partitioning, RLS, vacuum, replication, online DDL): use `postgres-patterns` or `mysql-mariadb`.
- N+1 queries generated by an ORM: start with `orm-patterns`, then return here.
- Warehouse cost tuning on BigQuery: use `bigquery`.

## Workflow

1. **Find the statements that matter** by total time, not by the one a user complained about.

   ```sql
   -- PostgreSQL (pg_stat_statements)
   SELECT calls, round(total_exec_time::numeric) AS total_ms, round(mean_exec_time::numeric, 1) AS mean_ms,
          rows, left(query, 100) FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 15;
   ```

   MySQL: `performance_schema.events_statements_summary_by_digest` or the slow log. On Cloud SQL, use Query Insights.

   **Check:** You have a ranked list and a target (for example "p95 under 50 ms" or "total time down 50%").

2. **Reproduce with real parameters and volume.** Capture actual bind values from logs. A plan on a 1,000-row dev table says nothing about a 50-million-row table.

   **Check:** The slow timing reproduces on a production-like copy or a read replica.

3. **Read the plan with execution data.** PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)`, MySQL 8.0.18+ `EXPLAIN ANALYZE`, MariaDB `ANALYZE FORMAT=JSON`. For writes, wrap in `BEGIN; ... ROLLBACK;` because `ANALYZE` executes the statement. Use the plan signals table below.

   **Check:** You can name the node that spends most of the time and why.

4. **Form one hypothesis and apply one change**: an index, a rewritten predicate, fresher or richer statistics, or a restructured query.

   **Check:** The plan changed in the way you predicted.

5. **Measure again** with the same parameters, several runs, cold and warm. Then check the write cost of any new index on the table's insert and update rate.

   **Check:** The target is met and no other top statement regressed.

6. **Lock it in.** Add a regression guard where practical: a test that asserts the query count per request, a plan check in CI, or a dashboard alert on mean time. Index creation on shared databases goes through a reviewed migration (`CREATE INDEX CONCURRENTLY` in PostgreSQL) with user confirmation.

   **Check:** The change ships as a migration, not a manual console edit.

## Reference

### Plan signals

| Signal | Likely cause | Typical fix |
| :--- | :--- | :--- |
| Seq scan or `type: ALL` on a big table, few rows returned | No usable index, or non-sargable predicate | Index matching the filter; rewrite the predicate |
| Estimated rows far from actual (10x or more) | Stale or insufficient statistics, correlated columns | `ANALYZE`; raise the column statistics target; extended statistics |
| Nested loop with many outer rows | Misestimate picked the wrong join | Fix the estimate first; then index the inner join key |
| `Rows Removed by Filter` large | Index finds too many candidates | Composite index adding the filtered column |
| Sort spills to disk, `Using filesort` | No index providing order, or low sort memory | Index in `ORDER BY` order; raise `work_mem` per session for reports |
| `Heap Fetches` high on index-only scan | Visibility map stale | Vacuum the table |
| Hash join with large batches | Hash table exceeds memory | Reduce input rows earlier; tune memory for that session |

### Index design

1. Equality columns first, then one range column, then sort columns.
2. Add `INCLUDE` (PostgreSQL) or extra trailing columns (MySQL) to make hot reads index-only.
3. Partial indexes for hot subsets (`WHERE status = 'open'`).
4. Every index costs write time, memory and vacuum work. Drop unused ones (`pg_stat_user_indexes.idx_scan = 0`, `sys.schema_unused_indexes`) after checking replicas and periodic jobs.

### Sargable rewrites

| Slow form | Fast form |
| :--- | :--- |
| `WHERE date(created_at) = '2026-11-01'` | `WHERE created_at >= '2026-11-01' AND created_at < '2026-11-02'` |
| `WHERE lower(email) = $1` without an expression index | Expression index on `lower(email)`, or a case-insensitive collation or type |
| `WHERE name LIKE '%son'` | Trigram index (PostgreSQL `pg_trgm`) or a search engine |
| `WHERE a = $1 OR b = $2` | `UNION ALL` of two indexed queries (dedupe if needed) |
| `WHERE id NOT IN (SELECT ref FROM t)` | `WHERE NOT EXISTS (SELECT 1 FROM t WHERE t.ref = x.id)`; `NOT IN` returns nothing if any `ref` is NULL |
| `WHERE varchar_col = 123` | Compare with a string literal of the column type |
| `SELECT DISTINCT` to hide join duplicates | Fix the join or use `EXISTS` |

### Statistics

- PostgreSQL plans from sampled statistics. After bulk loads run `ANALYZE table`. For correlated columns, `CREATE STATISTICS s (dependencies, ndistinct) ON city, zip FROM addresses;`.
- Prepared statements in PostgreSQL can switch to a generic plan after five executions; if one parameter value is very skewed, test with `SET plan_cache_mode = force_custom_plan` to confirm.

### Pagination

Use keyset pagination: `WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 50`, backed by an index on `(created_at DESC, id DESC)`. `OFFSET` reads and discards every skipped row, so page 1,000 costs 1,000 pages.

### Batch writes

| Task | Pattern |
| :--- | :--- |
| Bulk insert | Multi-row `VALUES` (hundreds to a few thousand rows per statement), PostgreSQL `COPY`, MySQL `LOAD DATA` |
| Insert from arrays | PostgreSQL `INSERT ... SELECT * FROM unnest($1::bigint[], $2::text[])` |
| Large update or delete | Loop by primary-key range in batches of 1,000-10,000, commit each batch, pause between batches, stop on replica lag |
| Upsert many rows | Stage into a temp table, then one `INSERT ... ON CONFLICT` or `MERGE` |

Run large write jobs only with explicit user confirmation on shared databases, make them resumable (record the last processed key), and watch locks and replication lag while they run.

## Anti-patterns

| Don't | Do instead | Why |
| :--- | :--- | :--- |
| Tune the query a user mentioned | Rank by total time first | The worst offender is often a fast query called a million times |
| `EXPLAIN` without `ANALYZE` | Execute with buffers on realistic data | Estimates hide misestimates and disk spills |
| Add an index per slow query | Design composite indexes that serve several queries | Index sprawl slows every write |
| Use query hints or forced plans first | Fix statistics, predicates and indexes | Hints freeze today's plan into tomorrow's data |
| `OFFSET` pagination for deep pages | Keyset pagination | Cost grows linearly with page number |
| One giant `UPDATE` | Batched, resumable updates | Long locks, bloat, undo growth and replica lag |
| Fetch rows in a loop (N+1) | One set-based query or a batched `IN` | Round trips dominate latency |

## Verification checklist

- [ ] The target statements come from a ranked list with a stated goal.
- [ ] The slowdown was reproduced with real parameters on realistic volume.
- [ ] Before and after plans were captured with execution data.
- [ ] Only one change was applied per measurement, and no other top statement regressed.
- [ ] New indexes were weighed against write cost and ship as migrations.
- [ ] Bulk writes are batched, resumable and confirmed by the user on shared databases.
